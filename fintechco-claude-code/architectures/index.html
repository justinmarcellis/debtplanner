How it works

  1. 1Arrive. App reports go straight to the service desk as they do today. Emails and call notes land in a secure inbox, and card numbers are masked to the last four before anything else reads them.
  2. 2Read. Claude reads each email and pulls out the claim: type, dates, amounts, merchant, card, and how the customer can be reached. Each field gets a confidence score.
  3. 3Look up. Through read-only connections to the mainframe and card systems, it finds the customers who could have sent it and ranks them, including related customers such as a joint account holder.
  4. 4Shape. It converts everything into the service desk's case format, so an email case looks exactly like an app case.
  5. 5Decide. The analyst sees the original email next to the prepared case and the top matches, and confirms with one click. Nothing is filed without a person.
  6. 6Learn. Each confirmation or correction is saved as a test case. A judge model scores every day's work, and Claude proposes rule and instruction updates that only go live after they pass the tests and a lead approves them.

Worth knowing
  • The investigation clock usually starts when the bank receives the report, so an email that waits a day in a queue is a day lost. Prepare cases on arrival.
  • Keep the match threshold strict. When two customers are close, show both and let the analyst choose; never file to a guess.
  • Start with the mainframe's existing read APIs. If there aren't any, a read-only query service in front of it is the first piece of work.
How engineers run Claude Code

Three ways engineering teams run Claude Code every day

The same foundation, applied where engineers work: on their own laptops, on every pull request, and during incidents. Each runs through our own Google Cloud project, under our IAM and logging, and puts a person where a change becomes real.

One set of rules on every machine

Governed laptops: Claude Code for every engineer

The everyday setup. People work in their own terminal and editor as they do today, and IT sets the rules from one place.

“This is the pilot's starting point. IT installs one settings file on every laptop, engineers sign in with their existing Google identity, and every model call is made with our cloud credentials and shows up in our audit logs.”

How it works

  1. 1Install the rules. IT's device management installs the company settings file on every laptop: permissions, hooks and the sandbox. Engineers can't change it.
  2. 2Ask. An engineer gives Claude Code a task. It reads the code and the team rulebook from the repository.
  3. 3Call the model privately. Each request leaves through the corporate proxy and reaches Claude through our own Google Cloud project, under our IAM.
  4. 4Check as it works. Hooks run before each edit and before Claude can say it's finished. The sandbox keeps commands off the open internet.
  5. 5Review. The engineer reviews the change and opens a pull request. Changes to the rules need the security team's approval.

Worth knowing
  • Start every team in Manual mode, set by the company policy, where Claude asks the engineer before edits and commands. Move a team to Auto mode only once the pilot data supports it.
  • Keep the settings file in a repository with required reviews, so a rules change is a reviewed change.
Every change checked, and every check graded

Pull request review, graded by a second model

Claude reviews every pull request before a person does. A separate judge model grades those reviews against a test set, so we know the reviewer is getting better, not just busier.

“An automated reviewer is only useful if people trust it. So every review is graded: a judge model checks each comment against the code, a weekly test of planted bugs measures what it catches, and reviewers' thumbs up or down keep the judge honest.”

  • Short-lived credentialSwapped for the job's identity; no stored keys

How the judge grades a review

A second Claude model, with its own rubric and no access to the reviewer's reasoning, scores each comment. Example scores from a weekly run:

CorrectIs the problem real in this code?0.92

Three signals, one gate
  • Judge scoresEvery comment, every pull request
  • Planted-bug test setCatch rate and false alarms, weekly
  • Reviewer thumbsKeeps the judge calibrated to people
A new prompt, rule or model ships only if all three hold or improve.

Scores shown are illustrative; the pilot sets the real baseline.

How it works

  1. 1Trigger. Opening a pull request starts a job on a short-lived runner inside our network, with a short-lived credential.
  2. 2Review. Claude reads the change and the team's rules, runs the tests and secret scan, and posts comments and suggested fixes.
  3. 3Grade. A separate judge model, with its own instructions, scores every comment for accuracy, severity and whether it can be acted on. Comments it rates as wrong are flagged for a person, not hidden.
  4. 4Test. Each week the reviewer runs against a fixed set of pull requests with planted bugs. Catch rate and false alarms are tracked over time.
  5. 5Calibrate. Reviewers' thumbs up and down are compared with the judge's scores, so we notice if the judge drifts.
  6. 6Gate. Any change to the reviewer's prompt, rules or model ships only if it matches or beats the current scores.

What it's worth, and how we measure it

Faster reviewsSeniors review a change that already passes the checksWe measure: Time to first human review
A reviewer we can trustEvery comment graded; wrong ones flaggedWe measure: Share of comments rated correct
Bugs caught earlyPlanted-bug tests measure it every weekWe measure: Catch rate on the test set
Safe to improveChanges ship only if the scores holdWe measure: Score change per release
Built-in safeguards
Claude can comment, never mergeRunner thrown away after each jobJudge uses a separate promptEvery call logged to the CI identity
Worth knowing
  • A judge model has blind spots too. Check a sample of its grades by hand every month, and keep the planted-bug set private so it isn't learned.
  • Grade on a fixed rubric with written examples. Vague questions like 'is this a good review?' give noisy scores.
A first look at every incident in minutes

On-call assistant: read-only investigation on every alert

An alert starts an investigation that can read but not change. The on-call engineer gets a summary with evidence, and a proposed fix to accept or reject.

“The first twenty minutes of an incident are spent gathering facts. Claude does that part as soon as the alert fires, with read-only access, so the on-call engineer starts from a summary instead of a blank screen.”
Trigger
  • Monitoring alertFor example, payment timeouts above normal
  • Incident topicOne message per alert starts a job
Claude investigates
  • Headless Claude Code jobRuns in Cloud Run with time and spend limits
  • Reads logs and codeThrough a read-only connector; card data redacted
  • Finds the likely causeWith the evidence that supports it
Behind the scenes
  • Read-only service accountCan read logs and code, nothing else
  • Claude through our Google Cloud projectOur IAM and logging; not used for training
  • Full recordWhat it read and concluded, attached to the incident
On-call decides
  • Summary in the incident channelLikely cause, evidence, next steps
  • Draft pull requestA proposed fix and a test
  • On-call engineerMerges through normal review, or closes it

How it works

  1. 1Alert. Monitoring fires and publishes a message that starts a short Cloud Run job.
  2. 2Investigate. Claude Code runs headless with read-only tools: it searches code and queries logs, but can't touch running systems.
  3. 3Summarize. It posts the likely cause with evidence in the incident channel.
  4. 4Propose. If the cause is in code, it opens a draft pull request with a fix and a test.
  5. 5Decide. The on-call engineer merges it through normal review, or closes it.

Worth knowing
  • Add this after the pilot, once incident data shows where triage time actually goes.
  • Noisy alerts will start noisy jobs. Fix alert quality first, or limit the assistant to the alerts that matter.
